# План: динамическое TCP-проксирование юнитов (Go L4 proxy)

Статус: **план, реализация не начата**
Дата: 2026-11-13
Область: доступ к TCP-сервисам юнитов снаружи docker-сети без перезапуска/перезагрузки прокси.

---

## 1. Контекст

Сейчас HTTP/WebSocket-трафик к юнитам проксируется nginx из `.docker/proxy/nginx.conf`:

- юнит — это dind-контейнер с именем `${UNITMAN_UNIT_NAME}.${UNITMAN_PROJECT_NAME}` (`compose.dind.yaml`);
- nginx резолвит `$unit.$project` через docker DNS `127.0.0.11` на каждое соединение;
- имя вида `port.unit.project.domain` разбирается через `server_name` и уходит на `http://$unit.$project:$port`;
- порты сервисов (внутри dind-контейнера) публикуются в netns юнита, поэтому `unit.project:port` доступен из сети `unitman_default`.

Для TCP такой схемы нет: в TCP нет `Host`/`SNI`, поэтому маршрутизация «по имени» невозможна. Нужен отдельный L4-прокси, который знает соответствие «внешний порт → `unit.project:внутренний порт`».

Дополнительное требование: **у одного юнита может быть несколько TCP-портов**, и внешние порты должны быть стабильными (ссылки в UI и у клиентов не должны меняться при рестартах).

---

## 2. Цель и границы

### Цель

1. Дать внешним клиентам доступ к любому числу TCP-портов юнита по схеме `host:<external_port>`.
2. Добавление/удаление юнитов и их портов — **без рестарта и без reload** прокси.
3. Внешние порты стабильны: `(unitID, internalPort) → externalPort` не меняется между стартами юнита и рестартами прокси.
4. Изменения состояния атомарны: при ошибке не остаётся «полузарегистрированных» портов.
5. HTTP/WS остаются на nginx; TCP не должен ломать существующую схему.

### Не входит в первую версию

- UDP (возможно отдельным этапом).
- TLS/SNI-мультиплексирование нескольких TCP-сервисов на одном внешнем порту.
- HTTP CONNECT-туннель.
- Замена nginx для HTTP/WS.
- Изменения UI, кроме отображения выданных портов (см. этап 3).
- Автоматическая генерация `ports` во внутреннем compose юнита (см. открытые вопросы).

---

## 3. Принятое решение

**Вариант A**: отдельный Go-контейнер `unitman-l4proxy` в сети `unitman_default`, публикуемый наружу фиксированным диапазоном портов.

Почему:

- docker DNS `127.0.0.11` доступен из коробки → `unit.project` резолвится так же, как в nginx;
- диапазон публикуется один раз, а внутри него слушатели открываются динамически через `net.Listen`;
- один процесс, никакой генерации конфигов и `nginx -s reload`;
- вся логика и состояние — в Go, легко интегрируется с раннером/вебом.

Ограничение варианта, которое принимаем осознанно: диапазон внешних портов фиксирован в `docker compose` и расширяется только перезапуском compose. Ёмкость считается заранее (см. §7).

## 4. Архитектура

```
клиент снаружи
     │  host:18001
     ▼
┌───────────────────────────────┐
│ unitman-l4proxy               │  сеть: unitman_default
│  - таблица маршрутов в памяти │  published: 18000-18999
│  - HTTP admin API :9000       │  state: /state/routes.json (volume)
│  - net.Listen на лету         │
└───────────────┬───────────────┘
                │ net.Dial("tcp", "iii.unitman:8000")
                │ (docker DNS, резолв на каждое соединение)
                ▼
      dind-контейнер iii.unitman
      (8000/8082/... опубликованы внутри)
```

Компоненты:

| Компонент | Ответственность |
|---|---|
| `unitman-l4proxy` | приём TCP, маршрутизация, открытие/закрытие слушателей, admin API, персистентность |
| unitman-web или раннер (владелец списка юнитов) | сообщает прокси полный список TCP-портов юнита (`PUT`), удаляет юнит (`DELETE`), отображает выданные порты |
| `unitman.yaml` | декларация портов и типов сервисов; добавляется тип `tcp` |
| внутренний `compose.yaml` юнита | публикует порты сервисов в netns dind-контейнера (уже требуется сейчас) |

---

## 5. Модель данных

Ключ маршрута — **стабильный ID юнита** (UUID из БД), а не имя. Имя/проект могут меняться; ID — нет.

```
Unit {
  ID      string          // UUID юнита
  Host    string          // "iii.unitman" (unitName + "." + projectName)
  Enabled bool            // открыты ли слушатели
  Ports   map[int]int     // internalPort -> externalPort
}
```

Инварианты:

1. Внешний порт уникален в пределах прокси.
2. `externalPort` для пары `(unitID, internalPort)` не меняется, пока юнит существует.
3. Внутренние порты одного юнита считаются уникальными (они публикуются в один netns dind-контейнера; два сервиса не могут слушать один порт).
4. Удаление юнита освобождает все его внешние порты.
5. `Enabled=false` сохраняет маппинг, но закрывает слушатели.

Если когда-нибудь один внутренний порт смогут занимать разные сервисы (разные bind-IP), ключ расширяется до `(unitID, service, port)` — но в текущей архитектуре это не требуется.

## 6. Admin API

Все вызовы — идемпотентные. Аутентификация: `Authorization: Bearer <token>`; API слушает только внутреннюю сеть, наружу не публикуется.

### `PUT /units/{id}`

Применяет полное желаемое состояние юнита.

Запрос:

```json
{
  "host": "iii.unitman",
  "enabled": true,
  "ports": [8000, 8082, 5432]
}
```

Ответ `200`:

```json
{
  "id": "01a1cba4-e678-70db-9bdc-99cf162a35ca",
  "host": "iii.unitman",
  "enabled": true,
  "ports": { "5432": 18000, "8000": 18001, "8082": 18002 }
}
```

Семантика:

| Ситуация | Поведение |
|---|---|
| юнит новый | всем портам выделяются внешние, слушатели открываются (если `enabled`) |
| порт уже был | внешний порт сохраняется, обновляется только `host` |
| добавлен новый внутренний порт | выделяется новый внешний, открывается слушатель |
| порт убран из `ports` | слушатель закрывается, внешний порт освобождается |
| `enabled=false` | маппинг сохраняется, все слушатели юнита закрываются |
| `enabled=true` после `false` | слушатели открываются на тех же внешних портах |
| ошибка `net.Listen` | полный откат, `409`, состояние не меняется |

### `DELETE /units/{id}`

Закрывает слушатели, удаляет маршруты, освобождает внешние порты. `204` / `404`.

### `GET /units`, `GET /units/{id}`

Текущее состояние — для UI и для reconcile-цикла.

Ошибки:

- `400` — некорректный JSON/порт;
- `401` — нет/неверный токен;
- `409` — нет свободных портов в диапазоне или порт занят;
- `404` — юнит не найден.

---

## 7. Аллокация внешних портов

- Диапазон задаётся конфигом прокси (`-port-min`, `-port-max`) и **должен совпадать** с опубликованным в compose диапазоном.
- Новому внутреннему порту выдаётся первый свободный внешний порт из диапазона.
- Выделение и резервирование — под одним мьютексом; порт резервируется в таблице маршрутов **до** открытия слушателя (иначе два новых порта в одном запросе получат один и тот же внешний).
- Освободившиеся порты переиспользуются (FIFO не обязателен).
- Ёмкость: `N_units × среднее число TCP-портов`. Пример: 1000 портов (18000–18999) при 5 TCP-портах на юнит ≈ 200 юнитов. При росте — расширить диапазон (требует одного перезапуска compose) или перейти к варианту с `network_mode: host`.

Альтернативы, которые рассмотрены и отклонены для v1:

- **Блок портов на юнит** (`base + index`) — проще, но тратит порты и ломается при изменении числа сервисов.
- **Детерминированный hash(unitID, port)** — не даёт гарантии без состояния и всё равно требует разрешения коллизий.
- **Отдельный IP на юнит** — тогда внутренний порт = внешний и прокси не нужен, но требует IPAM/маршрутизации в сети; оставить как запасной вариант при росте.

---

## 8. Состояние и восстановление

- Состояние — JSON-файл на volume: `/state/routes.json`; запись атомарная (tmp + rename).
- При старте прокси: читает файл, поднимает слушатели с **теми же** внешними портами.
- Если порт из состояния занят при старте — маппинг сохраняется, слушатель не открывается, ошибка логируется; повторная попытка при следующем `PUT`.
- При потере файла состояния маппинг будет выделен заново и старые внешние ссылки изменятся. Митигации:
  - volume обязателен;
  - опционально — хранить маппинг в Postgres/Redis (уже есть в инфраструктуре), файл оставить как кэш;
  - reconcile-цикл (см. §9) восстановит актуальный список юнитов, но не старые номера.
- Активные соединения при удалении маршрута не рвутся: закрывается только слушатель.

## 9. Интеграция

### 9.1. `unitman.yaml`

Добавить тип `tcp` рядом с существующими `http`/`ws`:

```yaml
services:
  db:
    ports:
      - port: 5432
        type: 'tcp'
```

Правило: в L4-прокси регистрируются только сервисы с `type: tcp`. `http`/`ws` продолжают идти через nginx.

### 9.2. Кто регистрирует маршруты

Два допустимых владельца (выбрать один, см. открытые вопросы):

**Вариант 1 — unitman-web.** Он уже парсит `unitman.yaml`, знает `services` и типы. На создание/старт юнита — `PUT /units/{id}`, на удаление — `DELETE`. UI сразу получает маппинг и показывает клиентам `host:port`.

**Вариант 2 — раннер.** В `NachatZapuskUnitaActivity` / `NachatOstanokuUnitaActivity` / `NachatUdalenieUnitaActivity` читать `unitman.yaml` (`gopkg.in/yaml.v3` уже в зависимостях) и дергать API:
- `up` → `PUT` с `enabled=true`;
- `down` → `PUT` с `enabled=false`, маппинг сохраняется;
- удаление юнита → `DELETE`.

Требование к обоим: после падения/рестарта веб или раннера должен быть reconcile.

### 9.3. Reconcile

Раз в N секунд (или при старте):

1. взять полный список юнитов и их TCP-портов из источника истины;
2. `PUT /units/{id}` по каждому;
3. `GET /units` у прокси, для юнитов, которых нет в источнике, — `DELETE`.

Идемпотентность `PUT` делает цикл безопасным.

### 9.4. Публикация портов внутри юнита

Чтобы `unit.project:port` был доступен, внутренний `compose.yaml` юнита должен публиковать порт (как сейчас `8082`). Варианты:
- оставить на авторов проектов (как сейчас);
- генерировать `compose.unitman.yaml` override из `unitman.yaml` (отдельная задача, вне v1).

Если порт не опубликован, прокси откроет слушатель, но `Dial` будет получать `connection refused`. Это штатное поведение: порт появится после исправления compose.

### 9.5. UI

- Показывать для каждого `type: tcp` сервиса выданный `externalPort` и готовый адрес `host:port`;
- при остановленном юните ссылку можно показывать, но помечать «не запущен» (`enabled=false`);
- при удалении юнита ссылка пропадает.

## 10. Инфраструктура

`common-services.yml`:

```yaml
unitman-l4proxy:
  build:
    context: ./.docker/l4proxy
  restart: always
  ports:
    - "18000-18999:18000-18999"
  volumes:
    - ./.docker/l4proxy/state:/state
  command:
    - "-api"
    - ":9000"
    - "-port-min"
    - "18000"
    - "-port-max"
    - "18999"
    - "-state"
    - "/state/routes.json"
    - "-token"
    - "${UNITMAN_PROXY_TOKEN}"
```

Требования:

- отдельный Dockerfile (multi-stage, `CGO_ENABLED=0`), без внешних зависимостей;
- API `:9000` не публиковать наружу;
- токен — из env, не в репозитории;
- healthcheck: `GET /healthz` (добавить в API);
- логи: старт/остановка маршрута, ошибки `Dial`/`Listen`, без спама на каждое соединение.

### Публикация диапазона и `docker-proxy`

При `"userland-proxy": true` (по умолчанию) Docker поднимает процесс `docker-proxy` на каждый опубликованный порт. Для диапазона в 1000 портов это заметно. Варианты:

1. `"userland-proxy": false` в `/etc/docker/daemon.json` — остаются только iptables-правила (проверить доступ к published-портам с localhost на целевых стендах).
2. `network_mode: host` для прокси — тогда публиковать ничего не нужно, но пропадает docker DNS; потребуется резолв `unit.project` через Docker API (см. альтернативы).
3. Уменьшить диапазон под фактическую ёмкость стенда.

## 11. Обработка отказов

| Сценарий | Ожидаемое поведение |
|---|---|
| Порт занят внешним процессом | `409`, полный откат, прежнее состояние сохранено |
| Закончились порты в диапазоне | `409` с текстом; маршрут не создан; нужен алерт/расширение диапазона |
| Юнит остановлен, `enabled=false` | внешние порты закрыты, маппинг сохранён |
| Целевой контейнер не запущен | слушатель открыт, `Dial` падает, клиент получает reset; после старта всё работает само |
| Контейнер пересоздан (новый IP) | docker DNS отдаёт новый IP на следующем `Dial`, ничего не делаем |
| Рестарт прокси | состояние восстанавливается, номера портов сохраняются |
| Прокси упал между `up` юнита и `PUT` | reconcile-цикл зарегистрирует юнит |
| Юнит удалён, а `DELETE` не дошёл | reconcile удалит лишние маршруты |
| Потеря `routes.json` | номера портов перевыделятся; старые внешние ссылки перестанут работать — требует volume и/или внешнего хранилища |

## 12. Безопасность

- Admin API — только внутренняя сеть + Bearer-токен.
- Прокси не должен давать доступ к произвольным адресам: `host` берётся из имени юнита/проекта, `internalPort` — из `unitman.yaml` (не из пользовательского ввода напрямую). Валидировать: `host` соответствует ожидаемому шаблону, порт 1–65535.
- Ограничение числа одновременных соединений на маршрут (env/флаг) — опционально, добавить при необходимости.
- Не логировать содержимое трафика.
- Клиентский IP на L4 теряется; при необходимости — PROXY protocol (`proxy_protocol` у бэкенда + библиотека на прокси), отдельная задача.

## 13. План тестирования

Прототип уже проверял базовые сценарии; в план фиксируем матрицу.

### Unit-тесты (без сети)

- аллокация: несколько новых портов в одном `PUT` получают разные внешние;
- идемпотентность: повторный `PUT` не меняет номера;
- добавление/удаление порта не сдвигает остальные;
- `enabled=false/true` сохраняет маппинг;
- упавший `Listen` → откат (маршруты/счётчики как до вызова);
- восстановление состояния из JSON;
- исчерпание диапазона → ошибка без частичных изменений.

### Интеграционные (docker)

- unit с 2–3 TCP-портами, все доступны снаружи через опубликованный диапазон;
- второй unit получает отдельные порты, пересечений нет;
- рестарт контейнера юнита: DNS-резолв на новое соединение идёт на новый IP;
- рестарт прокси: номера и доступность сохраняются;
- удаление юнита освобождает порты;
- `enabled=false`: соединение отклоняется, после `true` — снова работает;
- длинное соединение не рвётся при удалении маршрута (закрыт только слушатель);
- конфликт порта с внешним процессом → 409 и отсутствие мусора в состоянии.

### E2E

- клиент с хоста (вне docker-сети) подключается к `host:externalPort`;
- то же для клиента из другой docker-сети/другого хоста (при открытом firewall);
- `unitman-web` показывает корректный маппинг, ссылка работает после stop/start.

## 14. Этапы внедрения

| Этап | Содержание | Результат |
|---|---|---|
| 0 | Починить WS в nginx: `proxy_http_version 1.1`, `Upgrade`, `Connection` | WS работает через существующий прокси (независимо от TCP) |
| 1 | Сервис `unitman-l4proxy`: реестр, API, состояние, динамические слушатели, Dockerfile, сервис в compose | Прокси работает, управляется вручную через API |
| 2 | Тип `tcp` в `unitman.yaml`; регистрация из web или раннера; отображение внешних портов в UI | Полный цикл: юнит поднялся → порт доступен снаружи |
| 3 | Reconcile, `/healthz`, метрики/логи, лимиты, настройка `userland-proxy` и размера диапазона | Эксплуатационная готовность |
| 4 (опционально) | UDP, TLS/SNI-мультиплексирование, HTTP CONNECT, PROXY protocol | Расширение сценариев |

Критерии готовности этапа 1:

- несколько портов на юнит;
- стабильные внешние номера;
- отсутствие рестартов при изменениях;
- восстановление после рестарта;
- атомарность.

## 15. Открытые вопросы

1. **Кто владелец списка юнитов и портов** — unitman-web или раннер? От этого зависит, где вызывать API и где хранить выданные номера для UI.
2. **Когда выделять порты** — при создании юнита (ссылки известны заранее) или при первом старте? Рекомендация: при создании/подготовке, с `enabled=false` до старта.
3. **Поведение остановленного юнита** — закрывать слушатели (`enabled=false`, рекомендация) или держать открытыми и отдавать reset?
4. **Размер диапазона** на каждом стенде и допустимое число процессов `docker-proxy` / готовность менять `daemon.json`.
5. **Хранение состояния** — файл на volume (v1) или сразу Postgres/Redis.
6. **Генерация `ports` в compose юнита** из `unitman.yaml` — делать в рамках проекта или оставить авторам.
7. **Нужен ли `type: tcp` для HTTP-сервисов**, к которым ходят не браузером, а сырым TCP-клиентом (без Host-роутинга).
8. **UDP и TLS/SNI** — нужны ли в ближайшей версии.
9. **Ограничения по числу соединений и таймаутам** — нужны ли лимиты на маршрут.

## 16. Рассмотренные альтернативы

| Вариант | Плюсы | Минусы | Решение |
|---|---|---|---|
| nginx `stream` + генерация конфига + reload | знакомый стек, C-производительность | нужен reload при каждом новом юните, генерация файлов, монтирование каталога | отклонён |
| nginx `stream` + `ssl_preread` | динамика по SNI, без reload | только TLS, pass-through без заголовков | оставить для TLS-сервисов (этап 4) |
| Go L4-прокси, вариант A (bridge + диапазон) | без reload, docker DNS из коробки, простая интеграция | фиксированный диапазон, процессы docker-proxy | **принят** |
| Go L4-прокси, `network_mode: host` | любой порт без публикации диапазона | нет docker DNS, нужен Docker API/кэш IP | запасной |
| Отдельный IP на юнит (macvlan/static IP) | внутренний порт = внешний, прокси не нужен, любые TCP/UDP | IPAM, маршрутизация, клиенты ходят по IP | запасной при росте |
| Один порт + TLS SNI / HTTP CONNECT | минимум внешних портов | не работает для произвольного plain TCP без поддержки клиента | этап 4 |

## 18. Референс-проверка (до реализации)

Подход проверен прототипом вне репозитория (не добавлялся в код):

- несколько TCP-портов на один юнит;
- стабильность внешних номеров при добавлении/удалении портов;
- `enabled=false/true`;
- переживание рестарта прокси;
- атомарный откат при занятом порте;
- реальная цепочка «хост → контейнер-прокси → `iii.unitman:8082`» через опубликованный порт.

Этого достаточно, чтобы считать архитектуру валидной; код в репозиторий добавляется на этапе 1.
